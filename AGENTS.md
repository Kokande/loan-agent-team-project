# Правила работы с проектом

## Контекст

- Проект — агент поддержки кредитования малого и микробизнеса. Постановка, решения и открытые вопросы находятся в `README.md`; исходная схема — `Screenshot_20261029_232409.png`.
- Целевая архитектура: `frontend/`, Python-сервис в `backend/`, PostgreSQL + pgvector, общий запуск через `docker-compose.yaml`.
- Стек backend: FastAPI и LangChain/LangGraph. Не считай выбор конкретной связки библиотек завершённым без отдельного решения.

## Базовые правила

1. Перед изменениями изучи актуальные файлы и инструкции в затрагиваемых каталогах. Сохраняй чужие незавершённые изменения.
2. Делай минимальные изменения в рамках задачи. Не добавляй зависимости, рефакторинг и функции без необходимости.
3. Отделяй реализованное поведение от планов. Не превращай открытые вопросы из `README.md` в утверждённые требования; явно отмечай допущения.
4. Документацию и пояснения пиши по-русски; в коде используй понятные английские имена.
5. Сохраняй разделение ответственности: frontend отвечает за чат, backend — за оркестрацию агента, RAG и инструменты; доступ к БД выполняется на стороне backend.
6. При изменении API учитывай асинхронную работу `/api/v1/invoke` и `/api/v1/get`. Фиксируй согласованные контракты и обновляй frontend вместе с backend.
7. Учитывай предусмотренные схемой поведение сессии и очередь: обновление страницы начинает новый чат, сообщения во время работы агента поступают в очередь.
8. Ответы по нормативным вопросам опирай на найденные документы. Не выдумывай условия кредитования и данные клиентов; при нехватке информации учитывай передачу оператору. Критерии передачи требуют отдельного определения.
9. Не добавляй в репозиторий секреты и реальные персональные данные клиентов. Для примеров и проверок используй синтетические данные; настройки передавай через окружение.
10. Проверяй изменённое поведение доступными средствами. Для RAG проверяй релевантность найденных чанков, для агента — результат затронутого сценария. При изменении только документации достаточно проверить содержание, ссылки и diff.
11. Не заявляй об успешных проверках без запуска. Если проверка недоступна, укажи причину. Обновляй документацию при изменении архитектуры, API или способа запуска.
